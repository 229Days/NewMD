# ADR-0001: 仿 Typora 的 Markdown 编辑器 —— 总体架构决策

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-29
- **项目代号**: NewMD（正式产品名待定，见「未决问题」）
- **决策性质**: 绿地项目总体架构（greenfield）

---

## 1. 背景与目标

要做一个**仿照 Typora** 的 Markdown 编辑器。Typora 的核心辨识度在于：

1. **无源码的所见即所得** —— 输入 `# ` 立刻变标题，光标在渲染后的元素里移动，不出现左右分栏；
2. **完整的排版质感** —— 主题、专注模式、打字机模式、大纲、大文件性能；
3. **扩展渲染** —— LaTeX 数学、Mermaid 图表、代码高亮、脚注、表格；
4. **扎实的周边** —— 文件树、多标签、导出 PDF/HTML/Word、图片粘贴自动化。

本项目目标是在 Windows 桌面端复现上述体验，并保证产出的 `.md` 文件在 GitHub / VS Code / Obsidian 中基本可读。

**非目标（明确不做）**：实时多人协同、云同步、移动端、插件市场、团队/权限。

---

## 2. 已定决策

### 2.1 平台形态：Tauri 2 桌面 + Web 核心

**决定**：编辑器核心为纯 Web 应用（React），用 Tauri 2 作为桌面壳；核心不依赖任何 Tauri API，可在浏览器中以「受限模式」运行（用 File System Access API 降级）。

**理由**：

- 需要真正的本地文件系统访问（文件夹工作区、图片落盘、导出）；
- Tauri 安装包 ~10MB、内存占用低，与「轻量 Markdown 工具」定位相符（Electron 为 150MB+）；
- Web 核心与桌面壳解耦，使得纯 Web 部署、单测、E2E 都不需要起桌面进程。

**代价**：Windows 上依赖 WebView2（Win11 自带）；Rust 侧能力需要自己写 `#[tauri::command]`。

**被否决**：Electron（体积/内存）、纯 Web（文件系统能力不足）、VS Code 插件（无法实现沉浸式 WYSIWYG）。

---

### 2.2 编辑范式：真 WYSIWYG + 源码模式切换

**决定**：默认为**真 WYSIWYG** —— 文档以渲染后的形态存在 DOM 中，Markdown 标记不在编辑区可见。`Ctrl+/` 切换到纯源码模式。

**理由**：这是「仿照 Typora」的定义性特征，也是本项目与 VS Code / Obsidian 编辑体验的根本差异。

**代价**：开发难度约为「源码+预览分栏」的 3–5 倍；对 Markdown 双向序列化、中文输入法、粘贴行为都提出严格要求。

---

### 2.3 编辑器引擎：Milkdown（ProseMirror + remark）

**决定**：采用 Milkdown 作为 WYSIWYG 引擎，底层为 ProseMirror，Markdown 解析/序列化走 remark/unified 生态。

**理由**：

- Milkdown 的 schema 由 remark 语法插件直接生成，**Markdown 往返序列化是它的设计前提** —— 而这正是本项目最大技术风险点；
- 官方插件已覆盖目标功能面的大部分：CommonMark、GFM、表格、列表、KaTeX 数学、Mermaid 图表、Prism 高亮、斜杠菜单、tooltip、剪贴板、缩进、历史；
- 底层是 ProseMirror，若 Milkdown 某处碰壁，可下沉到裸 ProseMirror，已写的 remark 序列化层可复用。

**风险与缓解**：Milkdown 社区规模小于 Tiptap、更新节奏一般。缓解：所有 Milkdown 调用收敛在 `src/editor/` 适配层内，不散布到 UI 组件；升级/替换引擎时只改这一层。

**被否决**：

- _Tiptap_ —— 维护更活跃，但 Markdown 双向转换靠第三方包，表格/数学/代码块的序列化规则要自己写并补测试，前期慢 2–3 周；
- _裸 ProseMirror_ —— 可控性最高但起步成本最高；
- _CodeMirror 6 装饰层_（Obsidian Live Preview 路线）—— 鲁棒性最好，但严格说不是真 WYSIWYG，与 2.2 冲突。

---

### 2.4 Markdown 方言：GFM + Typora 常用扩展

**决定**：

- **基线**：CommonMark + GFM（表格、删除线、任务列表、自动链接、@提及）；
- **常用扩展**：脚注、`==高亮==`、上标/下标、YAML front matter、目录 `[TOC]`；
- **可选扩展**（默认开启）：KaTeX 数学（`$...$` / `$$...$$`）、Mermaid 图表（` ```mermaid `）。

**互操作策略**：非标准语法在导出 HTML 时按语义降级（例如 `==x==` → `<mark>x</mark>`，Mermaid → 保留代码块 + 兜底渲染），保证在 GitHub 等环境中不至于乱码。

**被否决**：严格 GFM（无数学/图表，不符 Typora 手感）、完全对齐 Typora（会牺牲互操作）、重度自定义语法（离开本编辑器即乱码）。

---

### 2.5 v1.0 范围：接近完整 Typora

**包含**：

- 文件夹工作区、文件树、多标签、自动保存
- WYSIWYG / 源码模式切换、撤销重做、查找替换、多光标
- 标题、段落、列表（有序/无序/任务）、表格、引用、分割线、脚注、高亮、上下标
- 行内代码、围栏代码块（Shiki 高亮 + 语言选择 + 行号/换行开关）
- 图片粘贴 / 拖拽 / 本地路径插入，自动落盘 `./assets/`
- YAML front matter 可视化编辑
- KaTeX 数学、Mermaid 图表
- 大纲侧栏、专注模式、打字机模式
- 内置浅色/深色主题 + 用户自定义 CSS 注入
- 导出 PDF / HTML / DOCX / Markdown（带资源）
- 拼写检查（系统词典）、快捷键配置、中英双语界面

**明确不含**：Word 级复杂排版还原、云同步、插件系统、实时协同、移动端。

**代价**：范围显著大于常规 MVP，必须靠 2.7 的里程碑硬边界来控节奏。

---

### 2.6 前端栈：React 19 + TypeScript + Vite + Zustand + Tailwind

| 关注点   | 选型                                                              | 理由                                                                           |
| -------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 框架     | React 19 + TypeScript                                             | `@milkdown/react` 官方绑定；Tauri 文档/模板支持最好                            |
| 构建     | Vite                                                              | Tauri 默认，HMR 快                                                             |
| 状态     | Zustand（按 `workspace` / `editor` / `ui` / `settings` 切 slice） | 无 Provider 地狱，与非 React 层（编辑器实例）共享状态自然                      |
| 样式     | Tailwind CSS + CSS 自定义属性                                     | 主题切换/用户 CSS 注入靠变量层，不靠重写组件                                   |
| 代码高亮 | Shiki                                                             | 渲染质量最好（VS Code 同款 TextMate 语法），WYSIWYG 与导出 HTML 共用同一套高亮 |
| 包管理   | pnpm workspace（`apps/desktop` + `packages/*`）                   | Web 核心与桌面壳解耦的前提                                                     |

### 2.7 导出：纯前端管线

**决定**：

- **PDF**：Tauri WebView 打印（Chromium print-to-PDF），用 `@page` CSS 控制页边距、页眉页脚、分页符、目录书签；
- **HTML**：自写序列化器，产出单文件（内联 CSS）或带资源目录的多文件；
- **DOCX**：`docx` npm 库，手写 ProseMirror 节点 → OOXML 映射；
- **Markdown**：Milkdown 序列化 + 资源目录打包（zip）。

**理由**：零外部二进制依赖，包体小，完全离线可用。

**已知短板**：DOCX 中复杂表格嵌套与数学公式的还原度有限（`docx` 库本身的能力上限）。这是有意接受的取舍；后续若需要，可把 pandoc 作为**可选外部工具**接入，不影响主路径。

**被否决**：捆绑 Pandoc（包体 +30MB、需处理子进程/编码/路径）；纯 JS PDF 库（中文分页与排版质量不达标）。

---

### 2.8 工作区与资源模型：文件夹工作区 + 图片入 `./assets/`

**决定**：

- 以**文件夹**为工作区单位（左侧文件树），支持多工作区切换与「最近打开」；
- 粘贴 / 拖入 / 截图的图片**自动复制**到 `./assets/`（相对当前 `.md` 文件所在目录，可配置为工作区级 `assets/` 或自定义路径），文件名用 `YYYYMMDD-HHmmss-<hash8>.png`；
- `.md` 内写**相对路径** `![](./assets/xxx.png)`；
- 文件重命名/移动时做**引用重写**（至少覆盖同工作区内图片引用）。

**理由**：整个文件夹可拷贝、可上 git、可跨机器，不产生断链。

**被否决**：引用原位置（移动即断链）、base64 内联（文件膨胀、git diff 灾难、GitHub 预览卡）、应用沙箱存储（与外部工具不互通）。

---

### 2.9 源码模式：CodeMirror 6

**决定**：`Ctrl+/` 时卸载 Milkdown 实例、挂载 CodeMirror 6 载入原始 Markdown 文本；切回时用 remark 重新解析为文档。CodeMirror 6 同时用于 WYSIWYG 内嵌代码块的编辑体验增强。

**理由**：真源码、真 Markdown（可见 HTML 注释、未识别语法、精确空白）；CodeMirror 6 的多光标/查找替换/大文件性能都优于自己造轮子。

**代价**：切换时有解析开销与滚动位置映射；需要做「未保存修改」状态在两套编辑器间的一致性。

**被否决**：同实例 CSS 显示标记（非真源码）；同步双栏（光标映射与循环更新抑制是深坑，不值得）。

---

### 2.10 测试与质量门槛

**决定**：

1. **Markdown 往返 golden 测试（硬门槛）**：`md → ProseMirror doc → md` 必须字节级一致。覆盖 GFM + 全部扩展语法，含边界（表格内嵌斜体+删除线、列表嵌套、脚注交叉引用、front matter、数学块、围栏代码含特殊字符）。用 Vitest + 语法语料文件。
2. **关键路径 E2E**：Playwright 覆盖 —— 打开/保存/自动保存、WYSIWYG↔源码切换、图片粘贴落盘、查找替换、三种导出。Tauri 侧用 `tauri-driver`/WebDriver，或先在浏览器模式跑核心用例。
3. **手测清单**：中文输入法（微软拼音/搜狗）在标题、列表、表格单元格、代码块中的组合输入 —— 自动化难以覆盖，每次发布前过一遍。

**不强求**：UI 组件覆盖率、视觉回归。

---

### 2.11 常规工程约定（按惯例选定，无需再议）

| 项       | 约定                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 自动保存 | 800ms debounce + 失焦即存 + 崩溃后未保存缓冲恢复                                            |
| 设置存储 | Tauri Store 插件（JSON，位于应用配置目录），首启写入默认值                                  |
| 主题     | CSS 自定义属性层；内置 light / dark；用户 CSS 文件以 `<style>` 注入并可实时预览             |
| 查找替换 | 源码模式用 CodeMirror 内建；WYSIWYG 用 ProseMirror search                                   |
| 拼写检查 | 系统/WebView 内置 spellcheck（英文有效，中文不适用，界面如实说明）                          |
| i18n     | i18next，中文优先，全部文案外置                                                             |
| 快捷键   | 默认对齐 Typora / VS Code 习惯，设置面板可改                                                |
| 代码高亮 | Shiki，主题随应用主题联动                                                                   |
| 应用结构 | `apps/desktop`（Tauri 壳）、`packages/core`（编辑器核心）、`packages/ui`、`packages/export` |

## 4. 里程碑

| #      | 名称             | 交付物                                                                                       | 验收标准                                           |
| ------ | ---------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **M1** | 壳与文件 IO      | Tauri+React 骨架、打开/保存/另存、自动保存、设置存储、浅深主题                               | 能打开文件夹、编辑并保存一个 `.md`，重启后状态恢复 |
| **M2** | WYSIWYG 核心     | 标题/段落/列表/引用/分割线/行内代码/围栏代码块/表格/图片插入 + **往返 golden 测试框架**      | 语料库全绿；编辑→保存→重开内容无差异               |
| **M3** | 源码模式与多标签 | CodeMirror 6 源码模式、双向切换、查找替换、多标签、撤销重做一致性                            | 切换 1000 行文档无丢内容；多标签下脏状态指示正确   |
| **M4** | 工作区与外观     | 文件树、大纲侧栏、用户自定义 CSS、字体/字号设置、快捷键配置                                  | 主题切换即时生效；大纲点击可跳转                   |
| **M5** | 扩展渲染         | KaTeX 数学、Mermaid、脚注、`==高亮==`、上下标、front matter 可视化、图片粘贴落盘 `./assets/` | 扩展语法往返不丢；粘贴图片生成相对路径             |
| **M6** | 导出与体验       | PDF/HTML/DOCX/MD 导出、专注模式、打字机模式、拼写检查、i18n、打包安装                        | 中文 PDF 分页正确；DOCX 在 Word 中可打开且结构正确 |

每个里程碑结束时**必须**：跑完全部 golden 测试 + E2E + 中文输入法手测清单，并能给出一份可运行的安装包/浏览器构建。

## 5. 主要风险

| 风险                                  | 影响                     | 缓解                                                                         |
| ------------------------------------- | ------------------------ | ---------------------------------------------------------------------------- |
| Markdown 往返序列化丢失格式           | **高** —— 数据正确性问题 | M2 起建立 golden 语料库，作为合并硬门槛；语料随功能持续扩充                  |
| Milkdown 生态小 / 维护放缓            | 中                       | 调用收敛于 `editor` 适配层；底层 ProseMirror 与 remark 层可独立存活          |
| 中文输入法在 contenteditable 中的边界 | 中                       | 避开自造输入处理；手测清单覆盖微软拼音/搜狗；必要时对 composition 事件做隔离 |
| 中文 PDF 分页 / 字体嵌入              | 中                       | M6 专项验证；`@page` + 系统字体栈；分页符/孤行控制单独调                     |
| 「接近完整 Typora」范围过大           | **高**                   | 6 个里程碑硬边界，每档可交付；单个里程碑超期即砍该档内的非核心功能           |
| DOCX 复杂表格/公式还原度              | 低（已知取舍）           | 文档中如实说明；pandoc 作为可选外部工具留后路                                |

## 6. 未决问题

1. **产品正式名称与图标** —— 当前沿用目录名 `NewMD` 作代号。
2. **代码签名与自动更新** —— Windows 分发是否需要签名证书、是否接 Tauri updater。
3. **Word 导出复杂场景** —— 嵌套表格、数学公式在 DOCX 中的降级策略（保留图片 or 降级为文本）。
4. **拼写检查深度** —— 是否需要自建词典/自定义词表，还是就用系统能力。
5. **文件重命名/移动的引用重写范围** —— 只覆盖图片，还是覆盖所有相对链接（含跨文件链接）。
6. **是否要插件系统** —— 明确 v1.0 不做，但架构上是否预留扩展点（例如自定义 remark 插件挂载口）。
