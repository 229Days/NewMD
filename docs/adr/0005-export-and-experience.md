# ADR-0005: M6 导出与体验 —— 一条管线，四个后端

- **状态**: 已接受 (Accepted)
- **日期**: 2026-10-16
- **关联**: ADR-0001 §2.7（导出管线）、§2.10（质量门槛）、§2.11（i18n / 拼写检查）、§4（M6 里程碑）、
  §5（风险）、§6 未决问题 3 与 4、ADR-0002 §2.8（样式归属）与 §3 / §5（导出锚点）、
  ADR-0003 §2.7（找不到就跳过，不猜）
- **决策性质**: 一个里程碑的整体切分，外加四条导出后端各自的形状

---

## 1. 背景

动笔前核了现场，四条事实改变了做法。

**① 这一档里有两件早就做完了，还有一条门槛从来没执行过。**

- **i18n 是完成的**：`zh-CN` / `en-US` 双 locale 加一条 key 同构的守卫测试，M4 就在跑。M6 那一项名存实亡。
- **拼写检查只剩一个开关**：`setSpellcheck` 已经从 `MarkdownEditorHandle` 一路通到两个引擎的
  `contentDOM.spellcheck`，缺的只是设置面板里的入口 —— 也就是说，**它今天没有任何调用方**。
- **E2E 从未跑过。** ADR-0001 §4 给每个里程碑尾巴都挂着「跑完全部 golden 测试 + **E2E** + 中文输入法
  手测清单」，而仓里没有一份 `*.spec.ts`、没有 playwright 依赖 —— **M1–M5 一次都没跑，五个里程碑
  照样全标了 ✅**。这条门槛从来没有被执行过，只在 M6 上突然较真，是任意的。

**② `packages/export` 不存在，而 core 也不给它可用的入口。** `packages/core/src/editor/index.ts` 的
barrel 是**故意**只导出一个工厂与一个契约的（那段注释写明了理由：让 UI 长不出对引擎的意见）。于是
remark 链（`parse` / `parseTransformed`）、toc 与 inline-marks 的节点类型、Shiki / KaTeX / Mermaid
三个渲染器，从包外**一个都拿不到**。而这四样**没有一个是引擎形状的** —— 它们 import 的是
unified / shiki / katex / mermaid，住在 `editor/` 是历史位置，不是 §2.3 那条边界的要求。

**③ 仓里没有任何正文排版样式。** 三份源 CSS（`editor/highlight.css`、`editor/toc.css`、
`ui/src/styles.css`）加起来只管主题变量、应用外壳、front matter / mermaid / toc 三个小组件、以及
Shiki 暗色那一行。`--editor-font-size` / `--editor-line-height` / `--font-editor` /
`--editor-max-width` 这四个设置项**只有 CodeMirror 在用**（`codemirror.ts:66-77`），WYSIWYG 正文
一个都没接。所以「屏幕上什么样，导出就什么样」这句话，今天**无内容可依**。

**④ ADR §2.7 里 DOCX 那一行的输入不是另外三行的输入。** 它写的是「手写 ProseMirror 节点 → OOXML
映射」，而 ProseMirror doc 只在一个活着的 WYSIWYG 编辑器里存在 —— 从 `MarkdownSurface` 里掏出它，
要在 ADR-0001 §2.3 的边界上开一个洞。

还有两条实测数字，直接决定了 HTML 那一节的取舍：Shiki 的 `highlight()` 已经往每个 token span 写了
内联 `color` 与 `--shiki-dark`（所以导出**不需要**为代码块带任何 CSS，只差 `highlight.css` 那一
行）；KaTeX 的 `katex.min.css` 24.8KB，而字体目录 1.2MB 里三份格式重复，**woff2 子集只有 20 个文件
296KB**。

## 2. 决定

### 2.1 M6 的完成定义，按事实写

**交付物**：四种导出（HTML / PDF / DOCX / Markdown）、专注模式、打字机模式、拼写检查开关、
打包安装。**i18n 从这一档划掉**（§1 ①）。

**验收**：中文 PDF 分页正确；DOCX 在 Word 中可打开且结构正确；golden 全绿；中文输入法手测清单过
一遍；能给出一个可运行的安装包。

两条验收标准原样保留 —— 它们是这一档里唯一可证伪的东西。

### 2.2 E2E 从所有里程碑的验收里移出去

ADR-0001 §4 那句「每个里程碑结束时必须：跑完全部 golden + **E2E** + 中文输入法手测清单」改成只
留 golden 与手测；E2E 记成一条**独立、没人认领**的工作，与 HANDOFF §5.1 那两类并列。

**理由**：一条从来不被执行的要求，作用只有一个 —— 训练读者忽略要求。之前两次踩过的坑
（ADR-0001 行 158「CodeMirror 自带多光标」、HANDOFF §4「源码模式多光标由 CodeMirror 自带」）都是
这么养出来的：一句写下来没人验的话，把真相藏了整整一个项目周期。验收条文第一次与事实一致。

**代价**：交付前没有自动化回归网，靠 golden 语料 + 两个包的行为测试 + 手测清单兜。这一条如实记在
§3。

### 2.3 一条管线，四个后端：输入统一是 mdast

导出侧拿到的是 `getContent()` 那串 Markdown（内存里的，含未保存的改动），自己 `parse` 成一棵
mdast —— 复用 core 已定的那条 remark 链 —— 四个后端都从这棵树出发。**DOCX 也走 mdast**，不按
ADR-0001 §2.7 原文走 ProseMirror 节点映射。

**理由**：ProseMirror doc 只在一个活着的 WYSIWYG 里存在。从 surface 里掏它要在 §2.3 的边界上开洞，
而那个洞一旦开了，「换掉 Milkdown 只改一个文件」这句话就不再成立；而且那样导出就绑定了「当前必须
是 WYSIWYG 模式」，源码模式下导不出。mdast 则严格不比 ProseMirror doc 少 —— 它是往返硬门槛钉着的
那棵树，而 toc / inline-marks / math 的节点类型本来就是 core 在 mdast 一侧的扩展。

**代价**：ADR-0001 §2.7 那一行要改（已改，见 §7 变更记录的对应条目）。

### 2.4 位置：独立包 `packages/export` + core 开一个窄 subpath

按 ADR-0001 §2.11 与 §3 的图建 `packages/export`。core 新增一个 subpath（`@newmd/core/document`），
把**非引擎的文档侧**导出来：`parseTransformed` 那棵 mdast、toc / inline-marks 的节点类型、Shiki /
KaTeX / Mermaid 三个渲染器、以及 §2.5 那份样式表。

`packages/export` 的依赖只有两个：`@newmd/core` 的公共 barrel（`getPlatform` 已经在那里，导出要读
图片字节）与这个新 subpath。

**理由**：`@newmd/core/editor` 的 barrel 是故意收窄的，所以今天 export 够不到 remark 链；而它要的
东西没有一个是引擎形状的。开一个 subpath 比把 `markdown.ts` 搬家便宜得多，也不动 `wysiwyg.ts` 的
任何 import。

**代价**：core 多一个公共 subpath，要靠一条测试钉住「它只导出文档侧，不导出引擎」——否则它会慢慢
长成第二个 `editor/`。

### 2.5 正文样式表住 core，且先把它补上

新建 `packages/core/src/document.css`，内容分两半：

1. **今天缺的那一半** —— 正文排版：`--editor-font-size` / `--editor-line-height` / `--font-editor` /
   `--editor-max-width` 接到正文上，加上标题、段落、列表、引用、表格、分割线、行内代码、链接、图片
   的规则；
2. **今天散在 ui 里的那一半** —— front matter / mermaid / toc 三个小组件的**阅读向**规则，从
   `ui/src/styles.css` 搬过来。

`packages/ui/src/styles.css` 用 `@import` 引入它给编辑器用；`packages/export` 用 `?inline` 取同一份
文本内联进导出物。

**理由**：core 是编辑器与导出**唯一共同依赖**的包，而且它已经在发 CSS（`highlight.css` /
`toc.css`）。ADR-0002 §2.8 自己就为 `toc.css` 留过这个例外，理由是「归并门槛 `markdown.ts` 也 import
那个模块」—— 而导出这条理由更成立。反过来让 `packages/export` 依赖 `@newmd/ui` 是不行的：那是一个
React 组件包，而导出与 React 毫无关系，依赖图上会多一条从低层指向高层的边。

这一份样式还是**专注模式的前提** ——「除当前段之外都变暗」需要段落级的规则，所以它不是为导出额外
扩张出来的，是 M6 路上本来就该补的一块。

**代价**：ADR-0002 §2.8 那句「样式写在 `packages/ui`」要改成三分：零件属性在 core、面向读取的样式
也在 core、应用外壳在 ui（已改）。

> **落地补记（2026-10-16，切片 ①）**：这份样式挂在 **`[data-newmd-document]`** 上 —— WYSIWYG
> 引擎把它设在自己的可编辑元素上，而不是设在外壳给的宿主上（Milkdown 在中间还夹着一层自己的容器，
> 挂高了会连宿主旁边的应用界面一起圈进去）。**导出侧包正文的那个元素必须带同一个属性**，否则内联
> 进去的规则一条都不生效。
>
> 同一条理由再往前一步：**这一份里不出现 `height: 100%` / `overflow` / `vh`**。它要同时喂给一块
> 视口和一页纸，而这两者对高度与滚动的答案正好相反 —— 滚动归外壳（见 §3 第一条）。

### 2.6 HTML：单文件，图片内联，公式按需带字体

导出一份自包含的 `.html`：

- **CSS 内联**（ADR-0001 §2.7 明说），内容就是 §2.5 那份；
- **图片 base64 内联**。导出 HTML 最常见的用途是「把这个文件发出去」，而 `./assets/` 一旦离开那个
  文件夹就全断 —— 那正是 ADR-0001 §2.8 花一整个决策去避免的事，导出侧不该把它再造一遍；
- **代码块一个字节的 CSS 都不用带**，只带 `highlight.css` 那一行（§1 的实测）；
- **KaTeX 的 CSS 与 woff2 字体按需内联**：文档里没有数学节点就一个字节不带，有才带
  （296KB → base64 约 395KB）。

**代价**：一个含公式的文档导出物约 400KB 起，且要写一段把 `@font-face` 里的 `url(fonts/…)` 换成
data URI 的改写。解不开的图片（新文档没有目录、路径指向工作区之外）**保留原相对写法**并计入报告，
不断链也不猜 —— 与 ADR-0003 §2.7 同一条原则。

### 2.7 锚点用位置 id

标题一律发位置 id：`<h2 id="newmd-h-3">`，序号是它在文档里的次序。`[TOC]` 展开成
`<ul><li><a href="#newmd-h-3">`，层级按 `level - minLevel` 缩进（与编辑器同一套算法）。**每个文档
都发 id**，不管有没有 `[TOC]`。

**理由**：文本派生的 slug 正是 ADR-0002 §2.6 拒掉的那套「第二个身份系统」，而且**中文标题会整段坍
成空串** —— 而中文正是本项目的主要场景。导出物是每次新生成的快照，没人会链进一个导出文件的锚点，
所以「稳定」在这里买不到任何东西；位置 id 则天然不撞。

**代价**：`#newmd-h-3` 不好看，也不能从 URL 猜出标题。

### 2.8 主题跟随当前，写死一份

导出时把当前主题的变量一起写进内联 CSS，产出**一个确定主题**的静态文件。

**理由**：与 §2.6 的「所见即所得」一致；导出物是快照，看它的人的应用主题与作者当时看到的是什么无
关。代码块白拿 —— Shiki 已经把两个颜色的 token 都写了。

**代价**：深色主题下导出的 HTML，贴进白底环境（例如 GitHub README 预览）看到的是深色纸。这是作者
自己选的。

### 2.9 PDF：隐藏 iframe + 系统打印，零新 Rust 命令

把导出的单文件 HTML 塞进一个隐藏的 `<iframe srcdoc>`，对 `iframe.contentWindow` 调 `print()`，弹
系统打印对话框，读者选「Microsoft Print to PDF」。`@page`（页边距、分页控制）写在那份 HTML 的
CSS 里。

**理由**：零新 Rust 命令、零新依赖；**一份 HTML 两用**（HTML 导出与 PDF 导出同源，只差打印样式）；
中文走系统字体栈（Windows 有微软雅黑），**不需要字体嵌入** —— 那正是 ADR-0001 §5 那条「中」风险最
省的走法；而且它在浏览器模式与桌面端行为一致。Rust 侧今天一条打印命令都没有，这条路不用加。

**代价**：位置与文件名由读者在系统对话框里选，应用管不到 —— 「另存为 PDF」实际是「打印成 PDF」。
iframe 打印在 jsdom 里测不到，进手测清单。

### 2.10 DOCX：图走 PNG，公式走源码

用 `docx` 库手写 mdast → OOXML 映射：

- **标题 / 段落 / 列表（含任务列表）/ 表格 / 引用 / 分割线 / 链接 / 行内代码 / 强调 / 删除线 /
  脚注**：真 OOXML；
- **Mermaid 走 PNG** —— `mermaid.render()` 已经直接给出一个自包含的 SVG 字符串，
  `svg → img → canvas → PNG` 是同一条 WebView 里的成熟链路；
- **数学公式降级为 LaTeX 源码** —— 行内用等宽字形，块级用一段等宽文本。

这个不对称不是随意定的，两边各自被「手上到底有什么」决定：图那边有一个可直接光栅化的独立产物，公
式那边 KaTeX 只会给定位过的 HTML 或 MathML，要出图就得引入 html2canvas 或赌 `foreignObject`——
那会是本项目里唯一一个「错了就静默出空白图」的环节。

这一条也是 ADR-0001 §6 未决问题 3（嵌套表格与公式的降级策略）的答案：**降级为文本，图除外**。

**代价**：光栅化那一段 jsdom 里跑不了，单独列手测。`docx` 的 `ImageRun` 到底吃哪些格式
（png/jpg/gif/bmp，以及吃不吃 SVG）**本 ADR 没有核实到** —— 网络被挡，这一条落地第一天就要用一个
最小测试钉住，别把方案建在记忆上。

### 2.11 Markdown：原文 + 图片，打一个 zip

导出物是当前 Markdown 原文（`getContent()`）加上它引用到的图片资源，打成一个 zip。需要一个新的
zip 依赖（倾向零依赖的小库）。

**理由**：这是一个「把一篇文档连同它的资源一起交出去」的动作，与 §2.8 的文件夹工作区模型一致。它
不需要 HTML 序列化器，所以可以独立于 §2.6 落地。

### 2.12 专注与打字机：两个引擎都做

- **专注模式**：WYSIWYG 用 decoration 给光标所在**块**打属性、其余变暗；源码模式给当前**行**。
- **打字机模式**：两者都在光标移动后把光标那一行滚到视口中间。
- 两个开关进 `AppSettings`（重启记住）与 `HOTKEY_ACTIONS`（于是自动出现在设置面板的快捷键配置
  里），默认键照 Typora：`F8` / `F9`。

**理由**：`Ctrl+/` 是一键切换的，半个矩阵失效比没有这个功能更糟 —— 与 ADR-0004 §2.5 拒掉「半个矩
阵的快捷键设置项」是同一条理由。

**代价**：四份实现（两个模式 × 两个引擎），且打字机模式的滚动在 jsdom 里测不到（没有布局），进手
测清单。

### 2.13 拼写检查：一个开关与一句实话

设置面板补一个开关（接上已经通了的 `setSpellcheck`），同一处如实写明「系统词典，英文有效，中文不
适用」，默认开。

这一条是 ADR-0001 §6 未决问题 4 的答案：**不建自定义词表**。浏览器与 WebView 的 `spellcheck` 是一
个晒不进去的黑盒，加不了词 —— 要做词表就得换掉整个拼写检查实现，那是另一件事。

**代价**：中文文档的拼写检查实际上是一个空开关。界面上说清楚了。

### 2.14 入口：工具栏一个「导出」，四个动作进快捷键表

标题栏工具栏加**一个**「导出」按钮，点开一个小下拉（HTML / PDF / DOCX / Markdown）；四个格式各进
`HOTKEY_ACTIONS`，于是自动出现在设置面板里，可在那里改键。全部文案双 locale。

**理由**：工具栏已经有 8 个按钮（新建 / 打开 / 文件夹 / 保存 / 另存 / 关闭 / 主题 / 设置），再加四
个就满了；而「导出」本来就是一个动词下的四个格式，天然是二级。进 `HOTKEY_ACTIONS` 是
ADR-0001 §2.11「设置面板可改」的直接兑现。

**代价**：新增一个小下拉组件与 5 组双 locale 文案。

### 2.15 切片的次序

| #   | 切片                                                                     | 为什么在这个位置                                       |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------ |
| ①   | 正文样式表（`core/src/document.css` + ui 接上 + 搬 front matter 那几段） | 同时是 HTML 导出的输入与专注模式的前提                 |
| ②   | `packages/export` 起壳 + `@newmd/core/document` + MD→HTML 序列化器       | 定形状：四个渲染器怎么复用、CSS 怎么内联、图片怎么内联 |
| ③   | HTML 导出的通路（导出下拉 + 保存对话框 + 写盘）                          | 让 ② 变成读者能按到的东西，也是 ④ 的基座               |
| ④   | PDF（隐藏 iframe + 系统打印）                                            | 撞 ADR-0001 §5 唯一那条「中」风险，也是两条验收之一    |
| ⑤   | Markdown + zip                                                           | 独立于 HTML 序列化器，最便宜的一条后端                 |
| ⑥   | DOCX                                                                     | 最大的一块，已知取舍                                   |
| ⑦   | 专注模式 / 打字机模式                                                    | 与导出完全无关，唯一可以自由挪的两片                   |
| ⑧   | 拼写检查开关                                                             | 一片，接上现成的通路                                   |
| ⑨   | 打包安装                                                                 | 收口                                                   |

**理由**：形状与风险先行。HTML 序列化器是 HTML 与 PDF 的共同输入，也是 ADR-0001 §2.7 决定过却从没
设计过的那一件；PDF 那条中风险越早撞越好。⑦⑧ 与导出之间没有依赖，放在任何位置都成立 —— 把它们放
在后面，是因为先做它们不会让任何风险提前暴露。

## 3. 代价与已知缺口

- **交付前没有自动化回归网**（§2.2）。靠 golden 语料 + 两个包的行为测试 + 手测清单。
- **PDF 的落盘位置由系统对话框决定**（§2.9），应用管不到。想做「导出 PDF 到指定路径」，得走
  WebView2 的 `PrintToPdfAsync`，那是将来另一件事。
- **`docx` 的 `ImageRun` 格式支持未核实**（§2.10）。落地第一天用最小测试钉住。
- **光栅化（SVG → canvas → PNG）在 jsdom 里测不到**（§2.10），进手测清单。
- **iframe 打印在 jsdom 里测不到**（§2.9），进手测清单。
- **打字机模式的滚动在 jsdom 里测不到**（§2.12），进手测清单。
- **数学公式在 Word 里是 LaTeX 源码**（§2.10）。想要真公式要自己实现 MathML → OMML，那是另一个
  大工程。
- **导出物是单一主题的**（§2.8）。深色文档贴进白底环境会看到深色纸。
- **`--editor-font-size` 等四个变量接上 WYSIWYG 之后，「导出的样子」才开始跟着设置走**。在此之前
  导出的样子与屏幕上看到的无关 —— 这一条写在这里是因为它曾经是隐形的（§1 ③）。
- **WYSIWYG 原本连滚动容器都没有**（切片 ① 动土时发现，已修）。`body` 是 `overflow: hidden`、外壳
  也是，CodeMirror 自带 `.cm-scroller`，Milkdown 一个都不带 —— 所以比窗口高的文档在 WYSIWYG 下够不
  到后半段。修法是**外壳滚动**（`EditorPane` 的宿主加 `overflow-y: auto`），不是让 `document.css`
  当滚动容器：后者会被内联进导出物，而导出物是一页纸。这条没有在真浏览器里量过，进手测清单。
- **GFM 任务列表在 WYSIWYG 里没有勾选框**（切片 ① 发现，**没有人认领**）。preset 只有 `checked`
  属性、没有对应的 view，`li[data-item-type="task"]` 到了 DOM 就是一个普通列表项。CSS 画一个框是
  做得到的，但那会是一个点不动的框 —— 与 [ADR-0004](0004-multi-cursor-scope.md) §2.5「一个只在半个
  矩阵里成立的设置项比没有这个设置项更糟」同一条理由，所以没画。要做就是一片（渲染 + 点击切换）。
- **两个新依赖**：`docx` 与一个 zip 库（§2.10 / §2.11）。都不在今天的依赖树里。
- **打包安装没有验过**：`pnpm tauri build` 从来没跑过，产物能不能装、装完能不能跑，是 ⑨ 的内容而
  不是假设。ADR-0001 §6 未决问题 2（代码签名与自动更新）**保持开放**。
- **golden 语料不需要新增**：这一档不碰序列化器，也不引入新的 Markdown 写法（HANDOFF §2 约束 2 的
  分界）—— 唯一的例外是两个新依赖与一个新包，都不在语法面上。

## 4. 被否决的方案

| 方案                                                       | 否决理由                                                                                                                                    |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 把 E2E 基建当 M6 的第一片做掉                              | M6 会显著变长（WebDriver 接 Tauri 是一整套基础设施），而这一片不产出任何读者能看见的东西；见 §2.2                                           |
| ADR-0001 §4 里保留 E2E 字样，只标注「M6 未含，待补」       | 留下一句已知不成立的要求 —— 正是行 158 那句「CodeMirror 自带多光标」的养法；见 §2.2                                                         |
| DOCX 按 ADR §2.7 原文走 ProseMirror 节点映射               | 要在 ADR-0001 §2.3 的边界上开洞；导出会绑定「当前必须是 WYSIWYG」；两套取数路径各修一次；见 §2.3                                            |
| 导出的输入是渲染好的 DOM（克隆 WYSIWYG 那份）              | 依赖活着的编辑器与已渲染的 NodeView；jsdom 里几乎测不了；DOM 里没有 mdast 的语义（代码块语言、脚注定义、表格对齐）要反推；见 §2.3           |
| 不建包，导出住进 `packages/core/src/export/`               | 「导出」与「编辑器核心」挤进同一个包，而导出不碰引擎、连编辑器都不需要挂载；见 §2.4                                                         |
| 先把文档侧从 `editor/` 搬到 `src/document/` 再导出         | 一次纯搬家重构，要动 `wysiwyg.ts` / `markdown.ts` 的 import 与若干测试路径，而收益只是命名更准；见 §2.4                                     |
| 导出自己写一份阅读/打印向的样式，编辑器不动                | 就是两套排版：读者在设置里调字体/字号/行宽，导出物一点变化都没有；见 §2.5                                                                   |
| 样式表住 `packages/ui`，导出反向依赖 ui                    | `packages/export` 会依赖一个 React 组件包，而导出与 React 无关；`pnpm` 还会把 ui 的依赖拉进导出的依赖图；见 §2.5                            |
| 导出 HTML 默认多文件（HTML + `assets/` 目录）              | 最常见的用途是「把导出物发给别人」，那变成一个目录；多文件还多一个 HTML 与 assets 分居两地的断链面；见 §2.6                                 |
| 公式只带 CSS 不带字体                                      | 省下 395KB，换来离线看公式时字形不是 Computer Modern（根号、分数线、积分号看得出差别）；见 §2.6                                             |
| 文本派生 slug 做锚点（照 GitHub）                          | 中文标题整段坍成 `section-n` —— 而中文是本项目的主场景；还要额外处理重名、Unicode 归一化、空串；见 §2.7                                     |
| 复用编辑器的 `(level, text, occurrence)` 编 id             | id 里带标题文本要处理百分号编码与长度；带 occurrence 又不比位置 id 更稳（改一个标题同样全移位）；见 §2.7                                    |
| 导出物同时写 light 与 dark 两套，跟 `prefers-color-scheme` | 导出物会与作者看到的**不一样**，「所见即所得」在导出上打折；而主题变量与零件样式要写两遍；见 §2.8                                           |
| 导出对话框里给一个主题选择项                               | 多一个对话框、一组双 locale 文案、一片测试面，而 v1.0 里这个选择绝大多数时候就是「跟随当前」；见 §2.8                                       |
| Rust 侧 `PrintToPdfAsync` 直接落盘                         | 一条平台专属的 unsafe 链路；适配器每加一个方法要同步 browser + tauri + 7 个 fake，而浏览器端只能降级回系统打印 —— 同一件事两条路径；见 §2.9 |
| 换掉当前窗口的 DOM 再 `window.print()`                     | 打印期间屏幕会闪；失败时读者停在导出物上而不是编辑器里；为了换回来要存编辑器状态 —— 一个数据丢失面；见 §2.9                                 |
| DOCX 里公式与图全部降级为文本                              | 全程纯文本、可单测，但 Word 里一张图都没有 —— 而图往往是 Markdown 文档里最想给人看的东西；见 §2.10                                          |
| DOCX 里公式也栅格化                                        | 要新引入 html2canvas 或赌 `foreignObject` 在所有 WebView 里都对，错了静默出空白图；见 §2.10                                                 |
| 专注/打字机只做 WYSIWYG                                    | 源码模式里开关是开的却没反应，读者分不清是坏了还是没做；见 §2.12                                                                            |
| 专注/打字机先做纯 CSS 版（不跟光标）                       | 「除当前段之外都变暗」与「光标永远在中间」都需要知道光标在哪，纯 CSS 做不到；做完还要再做一遍；见 §2.12                                     |
| 拼写检查加自定义词表                                       | 浏览器与 WebView 的 `spellcheck` 是黑盒，加不了词 —— 要做词表就得换掉整个实现；见 §2.13                                                     |
| 拼写检查不加开关，记为已完成                               | `setSpellcheck` 就是为这个开关存在的，不加就是一个没人调用的 API；见 §2.13                                                                  |
| 工具栏排四个导出按钮                                       | 工具栏从 8 个变成 12 个，窄窗口下先崩的就是它；而四个格式里常用的只有一个；见 §2.14                                                         |
| 导出只做快捷键，不进工具栏                                 | 本仓没有命令面板，于是这是四个只能靠快捷键发现的功能 —— 而设置面板是「配置」不是「使用」的地方；见 §2.14                                    |

## 5. 未决问题

1. **PDF 落到指定路径** —— 见 §3。要不要走 WebView2 的 `PrintToPdfAsync`，等系统打印这条路真的挡
   住了人再说。
2. **DOCX 的真公式** —— MathML → OMML 的转换要不要做（§2.10）。做了就是从「已知取舍」变成「一个
   独立工程」。
3. **导出工作区里的任意文件、或批量导出** —— 本 ADR 只定了「导出当前文档」。
4. **`[TOC]` 之外的内链** —— 文档之间的相对链接（`[另一篇](./notes/a.md)`）在导出 HTML 里仍然指
   向 `.md` 文件，而那个文件不在导出物里。要不要把它们也展开、或者降级成纯文本，本 ADR 没有讨论。
5. **代码签名与自动更新** —— ADR-0001 §6 未决问题 2，保持开放。
6. **任务列表的勾选框** —— 见 §3。渲染与点击切换都没有，目前是一个看不出是任务项的列表项。

**三项因本 ADR 而关闭的挂账：**

- **ADR-0001 §6 未决问题 3**（DOCX 里嵌套表格与公式的降级策略）**已决**：降级为文本，图除外（§2.10）。
- **ADR-0001 §6 未决问题 4**（拼写检查要不要自建词典）**已决**：不自建，用系统能力并如实说明（§2.13）。
- **ADR-0002 §3 与 §5 未决问题 2**（导出 HTML 里 `[TOC]` 条目的锚点方案）**已决**：位置 id
  `newmd-h-N`（§2.7）。
